## 行为准则

请尊重项目的每一位贡献者，保持友好和包容的态度。任何形式的骚扰或不当行为都是不可接受的。

## 开发流程

我们采用基于Git的工作流程：

1. Fork项目仓库
2. 创建功能分支
3. 提交变更
4. 确保测试通过
5. 发起Pull Request

## 分支命名规范

- `main`：主分支，保持稳定可发布状态
- `dev`：开发分支，日常开发工作的主要分支
- `feature/*`：新功能分支，如`feature/user-login`
- `bugfix/*`：Bug修复分支，如`bugfix/login-issue`
- `release/*`：发布分支，如`release/v1.0.0`
- `hotfix/*`：紧急修复分支，如`hotfix/critical-bug`

## 提交消息规范

请使用清晰、描述性的提交消息，遵循以下格式：

```
<类型>(<范围>): <描述>

[可选的详细描述]

[可选的脚注]
```

类型包括：

- `feat`：新功能
- `fix`：Bug修复
- `docs`：文档更改
- `style`：格式调整（不影响代码功能）
- `refactor`：代码重构
- `perf`：性能优化
- `test`：添加或修改测试
- `chore`：构建过程或辅助工具变动
- `ci`：CI配置文件和脚本的变更
- `docker`：Docker配置的变更

例如：

```
feat(auth): 实现用户登录功能

- 添加登录表单验证
- 实现JWT token生成
- 添加密码哈希处理

Close #123
```

## 代码风格

请遵循Go的标准代码风格和最佳实践：

- 使用`gofmt`格式化代码
- 遵循[Effective Go](https://golang.org/doc/effective_go)规范
- 通过`golangci-lint`检查代码质量

## 测试

- 为所有新功能和Bug修复添加单元测试
- 确保所有测试能够通过
- 尽可能提高测试覆盖率

运行测试：

```bash
cd tests
make test-all
```

## 文档

- 更新README.md和其他相关文档以反映您的更改
- 为API添加或更新注释
- 为新功能添加使用示例

## 容器化与CI/CD

在处理容器化和CI/CD相关功能时，请遵循以下规范：

### Docker相关

- 确保Dockerfile遵循多阶段构建最佳实践
- 使用特定版本标签而非`latest`作为基础镜像
- 优化镜像大小，减少不必要的依赖
- 在docker-compose文件中明确定义服务依赖关系
- 为容器添加适当的健康检查

### CI/CD相关

- 测试GitHub Actions工作流程需在本地执行验证
- CI工作流中包含代码质量检查、测试和构建步骤
- 更新CI配置时，确保提交消息中注明变更内容和原因
- 对于敏感信息，使用GitHub Secrets而非硬编码到配置文件

### 测试自动化

- CI流程中的测试必须覆盖所有主要功能
- 测试覆盖率应保持在80%以上
- 自动构建的Docker镜像应通过基本功能验证测试

## 问题报告

报告问题时，请包含以下信息：

- 清晰的问题描述
- 复现步骤
- 预期行为和实际行为
- 相关日志或截图
- 环境信息（操作系统、Go版本等）

## Pull Request

提交PR时，请：

1. 更新相关文档
2. 添加必要的测试
3. 确保CI检查通过
4. 填写完整的PR描述，说明解决的问题和实现方式
5. 如果适用，关联相关的Issue

感谢您的贡献！
